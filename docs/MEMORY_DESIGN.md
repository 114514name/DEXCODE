# DexLang 内存模型与 FFI 所有权 — 设计方案(讨论稿)

> 状态:提案,待讨论。目标是在**复杂度与开销之间取平衡**,尽可能消除内存泄漏
> 及其相关设计缺陷,同时**不改动语言表面的代码形式**(保留现有语法)。

## 1. 问题陈述

当前状态是"表面可用":程序能跑对,但内存只增不减,且语言与 C 之间没有所有权契约。
这不是一个功能,而是**一个缺失的设计**。具体表现为三个独立缺陷:

| # | 缺陷 | 现象 | 严重度 |
|---|---|---|---|
| D1 | 运行期堆值永不释放 | `CONCAT` / 原生字符串返回 / `MAKE_OBJ` 的分配无人回收 | 长驻程序内存无界增长 |
| D2 | FFI 字符串所有权未定义 | 原生函数返回 `const char*`,谁释放没有规定 | 库作者无法写出不泄漏的库 |
| D3 | 结构体语义与语法不一致 | 源码写法像值(`Box{...}`、无指针),VM 实现是引用 | 别名/环,阻挡任何回收方案 |

**D3 是 D1 的根因**:正因为结构体是引用语义,`let t = mk(); let b = Box{name: t}; t = "x";`
之后字段与局部槽指向同一块内存,任何"按槽释放"的方案都会造成悬垂。
实测把这一方案实现出来后,`return s;` 与对象字段两处立刻产生堆损坏崩溃。

### 1.1 实测量级

用统计分配器量出进程结束时的**保留堆**(不含解释器基础设施):

| 场景 | 保留堆 | 说明 |
|---|---|---|
| 空程序 / 局部变量赋值 ×1000 | **0 B** | 解释器基础设施(常量池、帧槽)释放正确 |
| 字符串拼接 ×1000(不增长) | 4,890 B | 每次一个短串 |
| 累计器 `s = s + "0123456789"` ×1000 | **5,006,000 B** | 泄漏量 ≈ 字符串长度 |
| 同上 ×5000 | **125,030,000 B** | **二次增长** O(n²) |

关键结论:**泄漏口径很窄**——只有 3 个分配点是垃圾
(`vm.c` 的 `value_concat`、`NCALL` 字符串返回、`MAKE_OBJ` 的 `Obj` 与字段数组),
其余 18 处堆分配(程序加载、常量池、帧局部槽)都有正确配对。

## 2. 结构性前提(决定方案空间)

这些都是**已经存在**的性质,方案应当利用而不是对抗:

| 性质 | 现状 | 为什么重要 |
|---|---|---|
| 字符串**不可变** | 全文无 `strcat`/原地修改;`CONCAT` 总是新建 | 引用计数安全,不会出现修改共享数据 |
| 变量**函数作用域** | `let` 在函数级分配槽,无闭包捕获 | 引用不会逃逸出函数(除返回值) |
| 结构体**无指针语法** | 源码只有 `Box{...}` / `b.f`,无取地址、无 null | 表面语义就是值;引用语义是实现选择 |
| 局部槽**静态定型** | 编译器要求能推断字段类型,否则报错 | 可以做按槽的静态决定 |
| 无用户级**资源/析构** | 没有 `Drop`/`defer`/句柄类型 | 不需要终结器,方案可以很简单 |
| 类型**动态、带标签** | `Value` 有 `type` 判别 | 运行期可区分,无需保守扫描 |

## 3. Rust 的启示与一个必须澄清的误解

你提到"Rust 没有 GC 也能避免泄漏"——这一点需要精确化,因为它直接决定方案选择:

- Rust 靠**仿射类型 + 编译期借用检查**(move 语义、`&`/`&mut` 排他性)在编译期证明
  无悬垂、无双重释放。**但它不回收环**:用 `Rc`+`RefCell` 造出的引用环同样泄漏,
  这正是 Rust 需要 `Weak` 的原因。
- Rust 的 `Rc` 是**引用计数**。也就是说 Rust 实际是"**所有权检查 + 引用计数**"两件工具,
  而不是"严密设计就不用任何运行期机制"。
- Rust 能这样做的前提是**静态类型 + 显式指针**:`&T` 与 `T` 在类型里区分得很清楚。

**对 DexLang 的推论**:DexLang 是动态类型、没有指针语法。
所以"Rust 式借用检查"在这里**没有着力点**——没有 `&` 可检查,值语义由编译器默默决定。
强行引入需要新增借用语法,那就改变了你只想保留的"代码形式"。

**但好消息是**:因为没有指针语法,DexLang 的**环只能由结构体自引用产生**。
把结构体定成真正的值语义(它本来就是这么写的),**环在类型层面就不可表达了**,
剩下的只有字符串,而字符串不可变、无环 —— 于是引用计数就**完备**了,
不需要环收集器,也不需要 GC。这是本方案的核心洞察。

## 4. 候选方案对比

| 方案 | 泄漏 | 悬垂风险 | 复杂度 | 运行期开销 | 改动语言表面 |
|---|---|---|---|---|---|
| A. 什么都不做 + 预算上限 | 仍有(O(n²) 有界) | 无 | **极低** | 0 | 无 |
| B. 结构体值语义 + 字符串引用计数 | **消除** | 低(需覆盖约 40 处) | 中 | 极低(O(1) per op) | 无 |
| C. 标记清扫 GC | 消除(含环) | 中(漏根即崩) | 高 | 中(STW 停顿) | 无 |
| D. Rust 式所有权 + 借用检查 | 消除 | 无(编译期保证) | **很高** | 0 | **需要新增指针/借用语法** |
| E. 仅 FFI 所有权契约 | 不解决 D1 | 无 | **极低** | 0 | 无(只改 `.dexdef`) |

## 5. 推荐方案:分层(先 E+A,再 B,GC 留作后备)

原则:**每一层独立可验证、可回滚,且都不改变语言表面。**

### 第 0 层:集中分配(基础设施,必须先做)

现状是 21 处堆分配**全部直接调 `malloc`**。没有单一入口,后面任何方案都无从插入。

```c
/* VM 的唯一堆入口;将来任何回收策略只改这一层 */
void *vm_alloc(size_t n);
void *vm_calloc(size_t k, size_t n);
void  vm_free(void *p);
```

本层不改变任何行为,但让"我们到底分配了多少"变得可观测。

### 第 1 层(方案 A):可见且有界

在 `vm_alloc` 里累加字节计数;超过可配置预算(默认如 256 MB)时以明确错误退出:

```
runtime error: 内存用量超过上限 (268435456 字节)
  常见原因:循环内字符串累加 (s = s + "x") 会按 O(n²) 增长
```

**价值**:把"静默无界、最后被杀"变成"有界、可诊断、指向原因"。
约 30 行,零悬垂风险,是后续所有工作的地基。

### 第 2 层(方案 E):FFI 所有权契约

这是**扩展性的核心缺口**,与 GC 无关,应当优先修:

1. **字符串只进不出**:规定原生函数返回的 `const char*` 是**借用**,
   VM 立即复制进自己的堆并接管;原生侧**不转移所有权、不得返回需要调用方释放的指针**。
   (现行 `xstrdup` 已经是这个行为,只是没写下来。)
2. **`.dexdef` 增加可选释放约定**,给需要动态分配返回值的库一条合法出路:
   ```
   refer "libfoo.dll";
   release dex_free;          # 可选:VM 复制完返回值后调用它释放原生缓冲
   extern func foo_name(id: int) -> string;
   ```
   VM 在 `xstrdup` 之后调用 `dex_free(ptr)`,把"谁释放"从"没人知道"变成契约。
   约 20 行,向后兼容(无 `release` 时行为同今)。
3. **文档化**:`.dexdef` 头部写明不变量。库作者从此有明确答案。

### 第 3 层(方案 B):结构体值语义 + 字符串引用计数

这一层才真正消除 D1,并且**不需要 GC**。

**3a. 结构体改为值语义**

源码本来就写成值(`Box{...}`、无指针),把 VM 实现对齐:

- `MAKE_OBJ` 建值;`STORE`/`SET_FIELD` 做**按字段复制**(不是共享指针)。
- 嵌套结构体由编译器在**编译期**解析成扁平字段布局,复制即 `memcpy`。
- 效果:`a.v = a` 成为类型错误(与 Rust 拒绝递归内联类型同理,错误信息现成:
  `cannot assign a value of type 'N' to field 'v' of type 'int'`)。
- **环在类型层面不可表达** → 不需要环收集。

*代价*:赋值时要复制。常见循环(`i = i + 1`)完全不分配,实测 0 字节,无影响。
*备选*:若结构体嵌套较深、复制成本不可接受,退一步只对**结构体本身**做引用计数
  (环仍可能泄漏,但可加编译期警告)——作为讨论选项保留。

**3b. 字符串引用计数**

字符串不可变,所以 RC 是安全且廉价的:

```c
typedef struct { uint32_t rc; char data[]; } VmStr;   /* 头部 4 字节 */
```

- `CONCAT` / 原生返回:新建,`rc = 1`。
- `LOAD`/`STORE`/`SET_FIELD`/`MAKE_OBJ`/`DUP`/压栈:按值复制,`rc++`。
- 槽被覆盖、帧销毁、对象值销毁:`rc--`,`rc==0` 时释放。
- **常量池字符串不参与 RC**(标 `owned=0`),永不释放。

*开销*:每次操作一个整数加减,O(1),与字符串长度无关 —— 在累计器场景下
比"什么都不做"的二次增长**更省**。实测该场景当前峰值 9 GB,RC 后应回落到 KB 级。

**3c. 为什么这比 GC 好(在这个具体设计里)**

- 没有 STW 停顿;对 `libdexxgal` 这类每帧渲染的游戏循环更友好。
- 不需要枚举根、不需要保守扫描 → **没有"漏根导致崩溃"这一类 bug**。
- 确定性释放:调试时内存曲线可解释。

| 层 | 内容 | 状态 |
|----|------|------|
| P0 | `vm_alloc`/`vm_calloc`/`vm_free` 收口全部 VM 堆分配 | **已完成** |
| P1 | `DEXCODE_MAX_MEM_MB` 预算 + 可诊断的 OOM | **已完成** |
| P2 | FFI 字符串所有权契约(`(string)->void` = 释放函数,`DXRL` 尾节) | **已完成** |
| P3 | 结构体值语义 + 拒绝递归类型 | **已完成** |
| P4 | 字符串引用计数 | **已实施后撤销**(理由见下) |

### P4 为什么撤销

P4 实现并测试通过(实测累加器 `while ... { s = s + "x"; }` 从约 13.6 GB 降到 5.1 MB),
但经重新评估后**主动撤销**,提交见 `git log` 中的
`Revert "feat(memory): P4 字符串引用计数"`。理由:

1. **无真实触发路径**。实测真实游戏循环(等待点击 + 每帧构造显示串)峰值仅 3.73 MB;
   全部示例代码里 `s = s + 变量` 这类累加模式为 **0 处**。
2. **收益与风险不对称**。引用计数的失败模式是**静默的**(悬垂/双重释放),
   而它只在本项目没有的实际负载下才有收益。实现过程中自己制造的 3 个缺陷
   (误删帧释放、`owned` 标记继承导致双重释放、`SET_FIELD` 未按值拷贝)
   全部靠测试才抓出 —— 这类代码"测试通过也不代表正确"。
3. **内存问题已被 P1 兜住**。没有 P4 时是"只增不减",但有预算上限与指向性诊断,
   不会静默涨到被系统 OOM 杀掉。

**重新引入的条件**:出现真实的字符串累积需求(例如某程序要用变量累积长文本,
或长时间驻留且大量拼接的服务端脚本)。届时 `git revert` 那个 revert 即可,
P3 铺垫的前提(槽独占对象副本、环不可表达)仍然有效。

### 当前(无 P4)的实际行为

- 字符串拼接(`CONCAT`)与原生字符串返回**不回收**,进程内只增不减;
- 结构体**可安全回收**(P3 值语义让槽独占副本),环在类型层面不可表达;
- 超预算时以明确错误退出,并指出"循环内字符串累加"这一最常见原因;
- 字符串累加仍是 **O(n²) 时间**(每次 CONCAT 必须复制整个累加串),
  这与内存无关,已在 README「已知限制」说明。

## 7. 明确不做的部分

- **不做 GC**(除非出现 P3 无法覆盖的环来源,例如将来加入数组/列表/闭包引用)。
  届时因为 P0 已把分配集中,插入标记清扫是增量工作,而非重写。
- **不引入借用语法**(`&`/`&mut`)。它要求静态类型与显式指针,
  与当前动态类型设计冲突,且违背"保留代码形式"的目标。
- **不追求"零泄漏"的绝对保证**:目标是**消除无界增长**并把所有权变成**有定义的契约**,
  而不是像 Rust 那样给出编译期证明。后者需要第 4 节方案 D 的代价。
