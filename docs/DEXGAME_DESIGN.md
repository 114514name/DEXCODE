**M2 期间对本文设计的三处修正**(以代码为准):

1. **相机约定改为「(x,y) 是显示在屏幕左上角的世界坐标」**。原设计里有"viewport/死区/
   边界钳制",落到实现时先定了一件更基础的事:相机 (0,0) 必须让**世界坐标 == 屏幕坐标**,
   否则无相机时整个世界被平移半个屏幕(M2 开发中真的写错过一次,被像素断言抓住)。
   取景居中要由用户/IDE 写成 `cam.x = target_x - 屏宽/2`。
2. **JSON 读写自己手写而不是 vendor jsmn/cJSON**。§7 曾写"vendor 一个小解析器";
   实际子集只有对象/数组/数/串/布尔,读写两端都在自己手里,`dg_json.c` 约 330 行就够,
   而且能顺手实现"跳过任意未知值"这一向前兼容的关键能力。见 §7.5。
3. **`parent` 在 JSON 里存"场景内索引",不是实体 id**。实体 id 含世代号、跨进程无意义;
   写场景时先给每个活实体编号,读回时再经 `id_map` 重映射为新的实体 id(M2 实现的
   `on_load` 钩子)。这一点在写第一版时搞错了(拿运行时 id 直接和槽位数比较),见 §5.4。


**M1 期间对本文设计的三处修正**(以代码为准):

1. **`MAX_NATIVE_ARGS` 从 8 提到 16**。设计时取了 8,但引擎 API 天然很宽
   (`eng_draw_uv` 有 10 个参数)。因为它只是 `param_types` 数组容量、不是格式约束,
   改动零成本。见 §3.4。
2. **DexLang 没有位移运算**,所以颜色不能由用户自行打包 —— 必须有
   `eng_rgba(r,g,b,a)` 这样的原生辅助。设计阶段未考虑到这一点。
3. **`eng_draw` 不能用"可选尾参"**。DexLang 编译器**精确校验参数个数**,所以
   `.dexdef` 必须把每个形参都声明出来。设计阶段的 `eng_draw(tex,x,y[,w,h,color])`
   写法不可用,已改为显式 6 参。

## 1. 这不是一个东西,是两个产品

| | 产品 A:引擎运行时 | 产品 B:可视化 IDE |
|---|---|---|
| 是什么 | 模块化 2D 游戏引擎(原生 DLL) | Scratch / UE 蓝图式节点编辑器 |
| 技术栈 | 纯 C + D3D11 + VM | HTML/CSS/JS + WebView2 外壳 |
| 给谁用 | 最终发布的游戏 | 开发期做游戏时 |
| 依赖 | **只有 libdexgame.dll + vm.exe** | WebView2(仅开发期) |
| HTML 的角色 | **完全不参与** | 就是 IDE 的全部 UI |

**关键澄清**:HTML **不进游戏**。最初的设想曾把 HTML 当作游戏的显示层(浏览器当渲染端),已否决——
发布产物不含任何 Web 依赖。HTML 只用于 IDE 的交互界面。

**顺序**:先做产品 A(M0.5–M4),因为 IDE 的数据模型必须由引擎的真实能力决定。
先做 IDE 会出现"画得出但引擎不支持"的空转。

产品 B 的设计另见本文 §9(占位),待产品 A 的组件清单冻结后再细化。

## 3. ABI 扩展(M0.5)— 本文档最关键的决策

### 3.1 问题

原生函数参数**最多 3 个**、类型只有 int/float/string、不能传结构体/指针/数组。

而引擎 API 大量天然是 4–6 参:`eng_new_object(x,y,layer,tag)`、
`eng_set_color(obj,r,g,b,a)`、`eng_query_aabb(x,y,w,h)`。
一路用「位打包 + 字符串属性袋」硬绕会让 API 很难看,且事后 retrofit 比现在做贵得多。

### 3.2 事实核查:不需要改字节码格式

读加载器(`vm/vm.c`)得到的关键事实:

```
vm.c:471-475   原生函数表条目 = name_idx(u16) | lib_idx(u16) | uint8 arity | uint8 ret_type   (NATIVE_FIXED_SIZE=6)
vm.c:476-485   param_types 正好 arity 个字节
vm.c:481       唯一上限:arity > MAX_NATIVE_ARGS(=8) 才拒
```

**`arity` 本来就是 `u8`,表条目本来就是变长的 `6 + arity`。** 所以支持 arity 3→8
**不需要任何格式改动、不需要升版号**。

真正的墙在**分发**,不在格式:

```
vm.c:912-1383  native_sig_supported() + NCALL 分发是按「arity × 类型组合」手写的 if 链
               arity 0/1/2/3 各有分支,末尾 else → die("unsupported native arity (max 3)")
```

按类型组合算是 3^N 条分支:arity4 = 81 条,arity5 = 243 条——**手写不可能**。
所以问题不是"放宽限制",而是"换一种调用约定"。

### 3.3 必须避开的坑:绝不能升版号

```
vm.c:364   if (data[4] != VERSION) { error: unsupported bytecode version }
```

版本检查是**严格相等**。一旦 `VERSION` 改成 4,所有现存 `.dexbc` 立刻全部失效,
正好违反"必须保证旧字节码兼容"的硬要求。
(`test_native.py`/`test_memmodel.py` 有现成的往返断言会抓到这一点。)

### 3.4 方案:双 ABI 并存,按 `.dexdef` 文件声明

| | 老库(std/math/img/ui/egui/gal) | 新引擎库 dexgame |
|---|---|---|
| ABI | **保持现状,一个字节都不动** | 值数组 ABI |
| C 函数签名 | `int f(int a, double b, const char *c)` | `int64_t f(const DexValue *args, int argc)` |
| 返回值 | 照旧 int/float/string/void | **照旧**(只改入参,不改返回,省一半复杂度) |
| 声明 | `extern func`(默认) | `.dexdef` 顶部加一行 `abi value_array;` |
| 字节码标记 | `ret_type` 高位置 0 | `ret_type` **bit7 置 1** |

**为什么用 `ret_type` 的 bit7**:`ret_type` 只用到 0–3 四个值(`NAT_VOID/INT/FLOAT/STR`),
bit7 是空的。这带来两个关键性质:

- **旧字节码 bit7 恒为 0** → 新 VM 解析结果与旧 VM **逐字节一致**,完全兼容
- **新字节码被旧 VM 读到** → `native_sig_supported` 拒绝 → 报
  `unsupported native signature`,是**明确报错而非错乱解析**

**白拿的性能好处**:VM 操作数栈上**已经就是带标签的 `Value`**,所以新 ABI 可以直接
`na->fn(stack + base, na->arity)` —— **零编组开销**,比老 ABI 逐参数 switch 转型还快。

**未来扩展的地基**:等真需要"传 DexLang 结构体/数组引用"时,往这个数组里加一个
"引用"标签即可,不必再改一次格式。

### 3.5 改动清单

| 文件 | 改动 |
|---|---|
| `dexlang/opcodes.py` | `MAX_NATIVE_ARITY` 3→8;新增 ABI 位常量 |
| `dexlang/defparser.py` | 解析 `abi value_array;` 指令;arity 校验改为按 ABI 分别限制 |
| `vm/vm.c` | 新增一个分发分支(复用现有编组循环);加载期识别 bit7 |
| `dexlang/pyvm.py` | **必须镜像**(否则 IDE 调试与真实运行不一致) |
| `docs/SPEC.md` | 4.5 节 + 5 节:新 ABI 的编码与语义 |
| `tests/` | 新 ABI 的声明/调用/往返/双 VM 一致性;老 ABI 的兼容性回归 |

**验收标准**:① 全部现有测试仍然通过(M0.5 当时是 686 项;现基线 915 项);② 现有 6 个库的 `.dexbc` 逐字节不变;
③ 新 ABI 能被两个 VM 一致执行。

## 4. 渲染架构(M1)

### 4.1 实测得到的设计约束

| 实测项 | 值 | 对设计的影响 |
|---|---|---|
| GPU | RTX 4060 Laptop,8 GB 专用显存 | 2D 批渲染是降维打击 |
| D3D11 | 硬件设备 S_OK,特性级别 **11_1** | 可用 flip 模型、多渲染目标、计算着色器 |
| WARP 兜底 | 也可用(11_1) | 无 GPU 机器可降级运行 |
| 显示器 | **2560×1600 @ 165Hz** | 一帧预算 **6.06 ms**,不是 16.7 ms |
| DPI | **150%**(SM_CXSCREEN 报 1707 = 2560÷1.5) | **必须声明 PER_MONITOR_AWARE_V2**,否则画面被拉伸再放大而糊掉 |
| 逻辑处理器 | 32 | 线程有余量(一期单线程,预留边界) |

### 4.2 管线

```
输入 → on_update(dt) 回调 DexLang → 组件系统(物理/动画/脚本) → 收集绘制命令
     → 按纹理/混合模式/层级排序 → 每纹理一次 DrawIndexedInstanced → Present(flip + VSync)
```

要点:
- **批渲染**:同纹理的精灵合并成一个 draw call;纹理图集是关键(避免图集切换导致批次碎裂)
- **层级/排序**:显式 layer + 同层 order,排序稳定
- **混合模式**:一期 alpha(预乘或直通,需定一)与 additive;乘法等后续加
- **帧节奏**:用 DXGI flip 模型 + `WaitForVSwapChain`,不用 `Sleep(16)`(现有 gal 的做法在 165Hz 下会锁死在 60)
- **无脏矩形**:全屏重绘是 GPU 的正常工作方式,不需要(现有 gal 的 CPU 合成才需要)
- **离屏渲染目标**:M1 就要有,既是像素断言的测试通道,也是二期后处理的入口

### 4.3 纹理采样:单纹素必须取纹素中心

M1 实测踩到的坑:用"区域边界"uv(如 `u0=x/W, u1=(x+1)/W`)画**单个纹素**时,
线性过滤会把邻居掺进来(纯绿读成 `0xff04ff04`)。所以引擎里固定这条规则:

| 源区域 | uv |
|---|---|
| 跨**多个**纹素 | **区域边界** `sx/W .. (sx+sw)/W` —— 1:1 绘制时屏幕像素中心正好落在纹素中心,放大时也不会整体缩半个纹素 |
| **单个**纹素(`sw ≤ 1`) | **纹素中心**(退化区间 `u0==u1`),即 `(sx+0.5)/W` |

这条规则在 `eng_draw_uv`(调用方给 uv)与 `eng_draw_scene`(引擎从 Sprite 的源矩形算 uv)
里都必须成立,分别由 `test_dexgame.py::test_atlas_png` 与 `test_scene.py::test_sprite_texel_rule`
锁住(后者实测:边界 uv 放大 4 倍后中心像素是 `0xFF20FF20`,纹素中心 uv 才是纯绿)。
**图集助手将来要自动完成的内缩就是这件事**,所以先在引擎里做对。

### 4.4 文字(DirectWrite)

- 矢量字形,任意字号清晰;自带 CJK 字体回退(系统有 `Microsoft YaHei UI`)
- 支持加载用户自备 `ttf`/`otf`(需要 `IDWriteFontFile` + 自定义字体集合)
- 排版能力按需暴露:换行(`DT_WORDBREAK` 等价)、对齐、行高、测量
  → 现有 gal 每帧量两次文字的做法要避免:**测量结果缓存**,只在文本/字号/宽度变化时重算
- 字形图集:**必须**(否则每个字符一个 draw call)

## 5. 实体与组件(M2)

### 5.1 模型

```
GameObject:  id(int) + 名字 + 变换(位置/旋转/缩放) + 父对象 + layer + 可见性 + 标签
             ↓ 挂载
Component:   引擎内置的一组:Transform / Sprite / Animation / Collider / Body /
             Camera / AudioSource / ParticleEmitter / Tilemap / Script
```

- **无物理的物体**:只挂 `Transform`(+ 可选 `Sprite`),靠 `eng_set_pos(obj,x,y)` 或每帧改坐标移动
- **有物理的物体**:再加 `Body`(+ `Collider`),由 C 侧物理步进驱动位置
  → 两条路径共用同一个 `Transform`,渲染层不关心谁在写它

### 5.2 组件清单(一期,全 C 内置)

| 组件 | 关键字段 | 备注 |
|---|---|---|
| Transform | x, y, rot, sx, sy, parent | 一切的基础;层级变换需缓存世界矩阵 |
| Sprite | texture, src rect, pivot, tint, flip, layer, order | 走批渲染 |
| Animation | 帧列表, fps, loop, 当前帧 | 或复用 Sprite 的 atlas 索引 |
| Collider | kind(AABB/圆/胶囊)、尺寸、offset、is_trigger、layer、mask | 与 Body 解耦,可单独用于触发区 |
| Body | motion(static/kinematic/dynamic)、velocity、gravity_scale、摩擦、弹性、是否休眠 | dynamic 才进物理求解 |
| Camera | viewport, zoom, rot, follow_target, 死区, 边界钳制 | |
| AudioSource | clip, volume, loop, 是否 3D 定位 | miniaudio |
| ParticleEmitter | 发射率、生命周期、初速、重力、颜色/尺寸曲线 | |
| Tilemap | 网格尺寸、图层、图块数据、碰撞层 | 见 §6.3 |
| Script | on_update/on_collision 等回调函数名(字符串) | 语言侧 `call()` 驱动,与 `eg_connect` 同思路 |

### 5.3 存储与可扩展性

定了「按可扩展设计」,所以:

- 一期用 **AoS**(每组件一个结构体数组 + 稀疏集/代际句柄),实现简单、可调试
- **代际句柄**(id = 索引 + 世代号),避免"删除后旧 id 误指新对象"——现有 6 个库都用单调不复用的 id,
  这是已知的坑(见 AGENTS §4),新引擎不重蹈
- 预留升级到 **SoA**(按组件类型分数组)的余地:组件存取全部经过访问器函数,不直接暴露内存布局

### 5.4 M2 落地实况(与 §5.1–5.3 的差异以此为准)

| 项 | 设计 | 实际 |
|---|---|---|
| 实体 | 有独立 GameObject 结构 | **只有槽位表**(`{gen, live}`),名字/layer/可见性/标签都没有 —— 它们要么属于渲染(Sprite 里已有 layer/order),要么等有真实需求再加。空结构体只是负担 |
| 组件种类 | 10 种 | 一期 **6 种**:transform / sprite / camera / animation / collider / body。audio / particle / tilemap / script 等到对应功能落地再加(加一种 = 加一张字段表 + 一行 `DEF[]`) |
| 运行时 vs 持久 | 未区分 | 字段表带 `persist` 位:`texture`(句柄)、`animation.time` 标注为运行时,不写进 JSON |
| 文档描述 | 未提 | **一种组件 = 一张 `DgField` 表**,JSON 的读与写遍历同一张表(§7.3 的结论)。`eng_field_count/name/type/persist` 把这四张表暴露给 IDE —— 这不是调试糖,是产品 B 生成属性面板的接口 |
| 变换层级 | 世界矩阵缓存 | M2 只做**位置**继承(带 `DG_MAX_DEPTH=32` 防环),旋转/缩放继承与缓存留到有需求时;`eng_world_x/y` 是唯一的读取口 |

```c

                 uint16_t size; uint16_t offset; } DgField;
```

## 6. 物理(M3)

> §6.1–6.3 是**设计意图**;§6.4 是本轮开工前锁定的决定(用户逐条拍板),
> §6.5 是**已实现的样子**与已知简化。三者不一致时以 §6.5 为准。

### 6.1 分层

| 层 | 内容 |
|---|---|
| L1 查询原语 | `overlap_rect/circle`、`point_query`、`raycast`、`sweep`、`query_aabb`(返回集合,需迭代器式 API) |
| L2 宽相 | **均匀网格/空间哈希**(不是四叉树:2D 场景实体尺寸相近时网格更快更简单) |
| L3 运动学 | 重力、速度、跳跃(土狼时间/跳跃缓冲)、斜坡、单向平台、**move-and-slide** |
| L5 瓦片 | 网格碰撞查询(比数百个独立碰撞体快得多) |

### 6.2 固定步长

物理用**固定步长 + 累加器**(建议 120 Hz),渲染帧率独立。
原因:可变步长会让跳跃高度、摩擦、碰撞穿透行为随帧率漂移,是 2D 平台游戏最经典的坑。
在 165Hz 显示器上尤其明显。

### 6.3 move-and-slide

平台跳跃的核心算法:一次移动按轴分解 + 逐步滑动,而不是"撞了就停"。
需要处理:斜坡(法线投影)、台阶、角落卡位、单向平台(仅从上往下穿过)。

---

### 6.4 M3 开工前锁定的决定(用户逐条确认)

| 问题 | 决定 | 理由 |
|---|---|---|
| 固定步长由谁驱动 | **默认自动**(`eng_frame_begin()` 内部按墙钟 dt 推进),`eng_physics_set_auto(0)` 后改手动 `eng_physics_step(dt)` | 默认零负担;但要能暂停/慢放/单步,调试与"回放"才有抓手 |
| 范围查询怎么返回(语言没有数组) | **游标式**:`query_rect/circle/point` 返回游标 id,`query_next` 逐个取(0 = 结束),用完 `query_end` | 语言侧用 `while` 就能遍历;命中集合存在 C 侧,不需要语言有数组。最多 8 条同时打开(可嵌套) |
| 射线/扫掠的多输出 | **结果槽 + 取值器**:`eng_raycast(...)` 返回 1/0,随后 `eng_hit_obj/x/y/nx/ny/t/tile` 读最近一次结果 | 结构体是值语义、原生返回只能是 int/float/string,所以"传引用出参"在当前语言里不可行;结果槽是唯一不需要改语言的方案 |
| 一期物理边界 | **运动学为主 + 简单 dynamic**:kinematic 走 move-and-slide;dynamic 只做重力/速度积分 + 轴分离解算,不做旋转/关节/堆叠;不做 Box2D | 与 §11 的"不做完整刚体动力学"一致;平台游戏 95% 的需求是运动学 |
| 瓦片地图的数据来源 | **独立文件/字符串**(`load_csv`/`load_file`),网格由 C 侧持有 | 图块数据可能几万格,塞进场景 JSON 只会让场景不可读;而且语言没有数组字面量 |
| 碰撞过滤 | **立刻启用 `layer`/`mask` 按位与** | 玩家/敌人/地形/触发区分层是 2D 游戏最实用的一个开关,M2 已经把字段建好了 |
| 单位与默认值 | 1 单位 = 1 像素、重力 **980 px/s²**(向下)、固定步长 **120Hz**、最大子步 8 | 与 M1/M2 的渲染坐标一致;980 是平台游戏的常见手感;120Hz 在 165Hz 显示器上余量充足 |

### 6.5 M3 落地实况(与 §6.1–6.3 的差异以此为准)

**查询与宽相**

- 形状:**AABB / 圆 / 竖直胶囊**(半径 `hw` + 半长 `hh`)。`transform.rot` **不参与碰撞**
  (2D 不引入 OBB)。重叠判定是**精确**的(胶囊按"两端圆 + 中间矩形"的并集拆分;
  胶囊-胶囊走线段距离)。
- 宽相:均匀网格空间哈希(单元默认 64px,哈希桶 2048),任何几何改动 `dg_phys_invalidate()`,
  下次使用时重建(O(n))。跨格形状去重用"每查询一代"的时间戳数组;超大形状进 overflow 列表;
  超大查询退化成线性扫描 —— 三条路径都有上界,不会退化到不可控。
- 碰撞解算用的是"**当前形状 vs 候选形状**"的离散重叠 + 轴向推出(`min/max`),不是连续碰撞检测。
  所以**子步上限必须小于最薄的障碍**:设为 **4px**(常见瓦片 8/16px),`eng_move` 内部自动拆步。
  极快的投射物应该用 `eng_raycast`/`eng_sweep_box`(它们是真正的射线/扫掠)。
- 物理在**世界坐标**里算,写回 transform 时减掉父链贡献 —— 有父对象的运动体也能工作。

**运动学**

- `move-and-slide` = 先沿 X 移动并对所有重叠障碍取"最紧的一侧"推出,再沿 Y 做一遍。
  滑动是自然结果(不需要法线投影);对 AABB 是**精确**的,落点可以直接断言。
- 每轴最多 4 轮解算(角落 / 多个障碍重叠时收敛)。
- dynamic 体:`v += g·gravity_scale·dt` → `friction` 只做水平阻尼 → move-and-slide →
  撞到就按 `restitution` 反弹(**速度低于 20px/s 或 restitution=0 就直接停**,避免抖动)→
  落地且速度极小时置 `sleeping`(用户设速度/位置会唤醒)。
- 接触状态(接地/贴墙/顶头)记在 `body.flags` 上,`eng_on_ground/wall/ceiling` 读它。
- **渲染插值**:有 `body` 的实体默认按 `alpha` 在"上一固定步"与"当前"之间插值,
  否则 120Hz 物理在 165Hz 上会看到"有的帧没动"。代价是画面**晚一个物理步**(插值的固有性质)。
  可用 `eng_render_set_interp(0)` 关掉(测试与像素断言常常要关)。

**瓦片地图(L5)**

- 新组件 `tilemap`:CSV 文本(逗号/空白分隔,**负数 = 空格子**,`0..255` 是图集索引);
  `solid[256]` 三态表(-1 = 未指定"非空即实心"/0/1),默认**非空即实心**。
- 数据**不进 JSON**(只存 `path`);字符串加载的图要用 `eng_tilemap_save_csv()` 自己落盘。
- 渲染走精灵批,**按可见矩形裁剪**(`view` 由相机算出),大地图只画看得见的部分;
  单纹素图集(`atlas_tile == 1`)同样遵守 §4.3 的"退化到纹素中心"规则。
- 碰撞:与实体碰撞体一起进 `move-and-slide` 的候选集(实心瓦片当 AABB 用),
  射线/扫掠同样会命中地形(`eng_hit_obj()==0 && eng_hit_tile()!=0` 表示"打到地形")。

**已知简化(接受,不是遗漏)**

| 简化 | 影响 | 何时该修 |
|---|---|---|
| 圆/胶囊作为**阻挡物**时,轴向解算按包围盒近似(重叠判定仍精确) | 圆角处的手感像方角 | 出现"草地上滚圆石"这类需求时 |
| 旋转不参与碰撞;层级只继承位置 | 旋转平台/缩放父对象不带动碰撞 | 出现真实需求时(要引入 OBB + 世界矩阵缓存) |
| 两个 dynamic 体互推只在各自的步里解算 | 叠罗汉/互相挤压会抖 | 需要堆叠时上"按质量解算 + 迭代求解器" |
| 单向平台 / 斜坡 / 土狼时间 / 跳跃缓冲**未实现** | 平台跳跃的"高级手感"要自己用 `eng_move` 拼 | 有真实关卡时;它们都是 `eng_move` 之上的策略层,不需要改内核 |
| 无连续碰撞检测(CCD) | 超过 4px/子步的极快物体仍可能穿过薄墙 | 用 `eng_raycast`/`eng_sweep_box` 或提高步长 |

## 7. 场景数据(M2 编辑期 / M7 导出期)

### 7.1 实测数据(决策依据)

| 实例数 | JSON 体积 | JSON 解析 | 二进制体积 | 二进制加载 |
|---|---|---|---|---|
| 1 000 | 366 KB | 5.6 ms | 106 KB | 0.07 ms |
| 10 000 | 3.7 MB | 39.6 ms | 1.05 MB | 0.67 ms |
| 50 000 | 18.5 MB | 218 ms | 5.3 MB | 3.35 ms |

(JSON 用 Python 的 C 实现测,速度与 jsmn 同量级或更慢;二进制按朴素逐字段写入估算。)

### 7.2 判断

**加载不在帧预算里**(是切关卡的一次性开销)。所以判据不是"快 30 倍",而是绝对值会不会被察觉:

- ≤1000 实例 → 约 2.8 ms(C 解析器)→ **无感**
- 10000 实例 → 约 20 ms → 一次轻微顿挫
- 50000 实例 → 约 109 ms → 该上二进制了

而 2D 游戏单个场景通常 100–2000 个实例。**收益真实,但不急。**

**真正的代价不在性能,在 schema 漂移**:开发期组件字段频繁增删,维护两套**手写**编解码
就是每次改两处,并产生"JSON 加了、二进制忘了"这种只在发布版复现的 bug。

### 7.3 结论:值不值取决于实现方式

| 做法 | 代价 | 结论 |
|---|---|---|
| 手写两套编解码器 | 每加字段改两处;漂移 bug 只在发布版出现 | ❌ 不值得 |
| **描述符驱动:一张字段表当唯一真相,两套编解码都遍历它** | 加字段 = 加一行表项,两格式自动同步 | ✅ 值得 |

### 7.4 推进节奏(比选哪种格式更重要)

1. **M2 只做 JSON**,但一开始就按描述符驱动实现
2. **M6.5/M7 导出时再加二进制**,复用**同一张表**
3. 加**一个通用等价性测试**:`load(json) → save(bin) → load(bin)`,全状态比对,自动抓漂移

**为什么必须延后**:二进制格式对**字段顺序**敏感且不容歧义。在 schema 天天变的阶段引入,
等于给移动靶建索引。**且二进制一旦发布到玩家手里就必须有版本号 + 迁移逻辑**,JSON 天然宽容
(按名字读、可缺可多),二进制不行。

### 7.5 M2 的实现与其代价(实测)

- **手写,不 vendor**:`dg_json.c` 约 330 行(流式写 + 游标读 + `djr_skip_value`)。
  读写两端都在自己手里,所以能直接实现"跳过任意未知值"—— 这是 §7.4 向前兼容的关键。
  唯一 vendored 的仍是 `stb_image`(283 KB 的解码器,自己写不值)。
- **游标式读取的契约坑**:迭代器(`djr_key`/`djr_arr_more`)**只报告"到头了",不代劳收尾**,
  也**必须自己消费元素间的逗号**。第一版两处都错(不消费 `}`/`]` 却让调用方再收尾;
  数组迭代器不消费 `,`),症状是 `line N: expected '{'` 这种看起来毫不相关的报错。
  现在报错信息会带上"实际看到的字符",一眼能定位。
- **向前兼容是真的**(不是设计口号):`test_scene.py::test_forward_compat` 构造带
  未知顶层键 + 未知组件 + 未知字段的场景,断言①能加载 ②能正常渲染 ③**回写一遍后
  未知的东西全被丢掉**。
- **实测规模**:2 个对象的场景往返(含渲染像素一致)在测试里稳定通过;
  §7.1 的 1000/10000 规模仍是估算,等 M7 导出期再实测。

## 8. 帧循环与 DexLang 接口(M4)

### 8.1 循环归属

C 侧拥有完整帧循环,每帧回调 DexLang 的回调函数(与现有 `egui` 的
"字符串函数名 + 语言 `call()`"同思路):

```
eng_run()                      // 阻塞,直到窗口关闭
  └ 每帧:
      输入采集 → on_update(dt) → 物理固定步进 → 动画/粒子 → 收集绘制 → 渲染 → Present(VSync)
```

DexLang 侧只写:

```
func on_start() { ... }
func on_update(dt) { ... }
func on_draw() { ... }
```

**为什么这样最优**:每帧仅约 1 次 FFI(实测 NCALL ≈ 9.5 ns,但更重要的是**批量数据不过 FFI**)。
实测 VM 指令吞吐约 370–420 MIPS,单帧预算内可容纳约 600–700 万条指令——
**语言层不是瓶颈**,所以把循环交给 C 不会牺牲用户表达力。

### 8.1b M4-a 落地实况(帧循环 / 输入)

**主循环**:引擎的帧生命周期一直在 C(`eng_frame_begin/end`:抽消息 → 采样输入 → 绑目标
→ 清屏 → 重置批次 →(自动)物理步进;结束:提交批次 → 帧节奏 → Present)。"每帧该调哪个
语言函数"这件事放在 **`libs/dexgame/dexgame_fast.dex`** 这个语言模块里: `eng_run(on_start,
on_update, on_draw)` 用 `call("名字")` 分发 —— 与 `egui_fast.dex` 的 `eg_app_run` 同一套路。
这样**不需要给 VM 加"反向调用语言函数"的机制**,代价是调度在语言侧(每帧几次 `call()`,
纳秒级)。帧内顺序:begin → on_update(dt) → on_draw → end;自动物理在 on_update **之前**
跑完,所以这一帧设的速度下一步生效(1 帧输入延迟,165Hz 下约 6ms);要完全掌控就
`eng_physics_set_auto(0)` 自己步进。

**输入**:两层接口。底层轮询给"我想自己解释按键"的人,动作映射给游戏逻辑与 IDE
(改键位只改绑定,不动逻辑)。按键码是**统一编号**,所以一个动作可以同时绑键盘/鼠标/手柄:

| 范围 | 含义 |
|---|---|
| 0..255 | Win32 虚拟键(65='A', 32=空格, 37/38/39/40=方向键) |
| 256..258 | 鼠标左/右/中键 |
| 300..313 | 手柄:上/下/左/右、Start、Back、LS、RS、LB、RB、A、B、X、Y |
| 400+i / 500+i | 手柄轴 i 的正向 / 负向(i:0=LX 1=LY 2=RX 3=RY 4=LT 5=RT) |

- 手柄走 XInput,运行时 `LoadLibrary("xinput1_4.dll")`(与 d3dcompiler 同样的做法,
  没插手柄也不该崩);摇杆有死区、`LY/RY` 取反让"下 = 正"与屏幕坐标一致。
- 边沿检测(pressed/released)靠"帧结束把当前记成上一帧"。**拷贝时机是关键**:
  放帧开始会把本帧新按下的键立刻当成"上一帧也按着",`pressed` 永远为假。
- `eng_input_feed*()` 可以注入合成输入 —— 无人值守环境里这是**唯一**能测输入的通道,
  IDE 的"脚本化试玩/回放"也用它。
- **实体名**(`eng_set_name/eng_name/eng_find`)是配套必需品:语言没有全局变量,
  回调函数看不到主程序的 `let`,跨帧状态只能放组件里靠名字取回。名字随场景 JSON 存取,
  也是 IDE 场景树要显示的东西。

### 8.1c M4-b 落地实况(音频)

**选型**:XAudio2(用户已确认)。与 D3D11 同一风格 —— 用系统 API,不往仓库塞第三方代码;
仓库里唯一 vendored 的东西仍是 `stb_image`(283KB 的解码器,自己写不值),而 WAV 解析
只要 ~120 行。miniaudio 虽然更全能(自带 mp3/ogg 解码),但那是 20 万行级别的单头文件。

**两层模型**(别混):

| 概念 | 是什么 | 为什么 |
|---|---|---|
| 声音资源 `eng_sound_load` | 按**路径缓存**的解码结果(取样率/声道/时长 + PCM 缓冲)| 同一段音效反复播放不该反复读盘/解码;`WAVEFORMATEX` 与 PCM 缓冲在播放期间必须保活,归它持有 |
| 播放实例 `eng_sound_play` | 一次播放(`IXAudio2SourceVoice`)| 同一个声音要能同时响多次:脚步、子弹、连击音 |

**平台细节**:

- XAudio2 是 COM 接口但**没有导入库**:运行时 `LoadLibraryA("xaudio2_9.dll")`
  (Win8 回退 `xaudio2_8.dll`)+ `GetProcAddress("XAudio2Create")`;每个使用它的线程要
  `CoInitializeEx`(已被别的模式初始化过就忽略)。
- **没有声卡不算致命**:`eng_audio_ok()` 暴露设备状态,`CreateMasteringVoice` 失败后
  所有播放调用都**带原因失败**,游戏照常跑(只是没声音)。测试据此 SKIP 而不是 FAIL。
- WAV 支持范围:8/16 位 PCM、单/双声道。非 PCM(float)、24 位、多声道会**明确拒绝并说明**
  (而不是"放不出声但不知道为啥")。mp3/ogg 不在范围里 —— 要就要额外的解码器。
- `audio` 组件让**场景能带声音**:`path`/`volume`/`loop`/`play_on_start` 持久,
  `handle`/`voice`/`playing` 是运行时;设置 `path` 时**立刻解码**(路径错了当场报,
  不要等到播放那一刻);卸载组件/删除实体会停掉在放的实例。

### 8.1d M4-c 落地实况(文字)

**路线**:DirectWrite 只负责"给我字形",渲染仍走引擎自己的 D3D11 批次 —— 不用
`IDWriteTextLayout::Draw`(那是往 GDI/DC 上画,与批次渲染是两条路)。

```
IDWriteFontFace::GetGlyphIndices + GetDesignGlyphMetrics   → 字形索引 / advance
IDWriteFactory::CreateGlyphRunAnalysis(单个字形)            → 分析器
  GetAlphaTextureBounds(CLEARTYPE_3x1)                     → 墨水外框(可含负坐标)
  CreateAlphaTexture(...)                                  → 3 字节/像素覆盖率位图
  取 R/G/B 最大值当 alpha(次像素能量分在三通道里,取最大值保住笔画粗细)
  → 货架式打进 512×512 图集(dg_tex_update_rgba 局部上传,1px 间隙防渗色)
  → 画字 = 白色四边形 + 顶点色 tint
```

要点与代价:

- **整数像素定位**:字形位图按整数像素光栅化,quad 也必须落在整数像素上,否则线性过滤
  会把位图糊掉(配合 §4.3 的"区域用边界"规则,1:1 映射清晰)。**推论:一期文字不支持
  子像素定位**,做平滑滚动字需要另找方案(缓存多份/2x 图集)。
- **两层缓存**:字体按(家族, 字号)复用;字形按(字体, 码点)缓存度量与位图 ——
  `eng_text_width` **不会**重新排版文字(现有 gal 每帧量两次文字是已知坑)。
- 度量直接来自字体度量(`designUnitsPerEm/ascent/descent/lineGap`),所以行高与基线是
  原生精度(16px 的 Microsoft YaHei UI:行高 20.32、ascent 16.25)。
- UTF-8 直接解码成码点(非法字节退化成 `?` 而不是报错);CJK 走系统字体集合,
  `中文字` 实测等宽 16px/字。
- **一期不支持**:换行/自动折行、对齐、富文本、字距调整、独立的粗斜体选择。
  图集满了会**明确报错**(要求减少字号种类或调大图集),不是静默丢字。

**静态内嵌变体**(M4-d):`dexgame_static.dexdef` 用 `refer static "libdexgame.dll"`,
编译时把 400KB+ 的 DLL 字节内嵌进 `.dexbc`,运行时由 VM 释放到临时目录再加载 ——
发布产物不需要外部 DLL 文件。`tests/test_static.py` 把外部 DLL 改名后跑离屏像素断言,
证明这条路真的通。

### 8.2 接口约定

- 全部函数 `eng_` 前缀;`.dexdef` 顶部 `abi value_array;`
- 提供 `dexgame.dexdef`(动态链接)与 `dexgame_static.dexdef`(`refer static`,字节内嵌,
  运行时无需外部 DLL)——沿用 gal 的既有做法,便于发布单文件
- **失败要带得出原因**:提供 `eng_last_error()` 返回字符串,而不是只返 -1/空串
  (这是现有 6 个库的共性缺陷,见 AGENTS §4)
- 返回字符串用共享静态缓冲(依赖 VM 的 `xstrdup` 复制语义)——沿用既有做法

### 9.3 B3 落地实况(与 §9.1 的差异以此为准)

**做出来的样子**

- **视口(center,`dexstudio/web/viewport.js`)**:视口里的画面就是引擎**离屏渲染**的一帧
  (1024×640,`eng_init_offscreen`),落成 BMP 后经**虚拟主机** `dexstudio-preview.local`
  被前端画到 `<canvas>` 上。为什么不把像素塞进 JSON:1024×640×4 ≈ 2.6 MB,
  base64 后每条消息 3.4 MB,这条通道会被压垮。
  网格、选中框、框选、瓦片格都画在**同一个坐标系**里(世界 → 图内像素 → 画布),
  所以不会出现"框和画面对不上"。
- **相机语义**:引擎的相机约定是"(x,y) = 屏幕左上角的世界坐标、zoom = 每世界单位像素数"。
  编辑器**不改用户的相机实体**(那会写进场景 JSON、污染撤销历史),而是用引擎新增的
  **视图覆盖** `eng_set_view(on,x,y,zoom)`;`dg_scene_active_camera` 优先返回覆盖值,
  于是渲染与"屏幕→世界"自动一致。产品 A 侧为此改了 3 处(新增 `eng_set_view`,
  `eng_object_id_at` 供 IDE 按序号枚举实体)。
- **属性面板**:完全由 `comp.schema`(`eng_comp_*`/`eng_field_*` 自省)生成 ——
  **引擎加组件,IDE 一行都不用改**;`persist=0` 的字段标"运行期",`tex_path`/`path`
  这类路径字段改错时把引擎的原因显示出来并标红。
- **图层**:按 `sprite.layer`/`tilemap.layer` 分组(不另造图层模型);
  顺序仍由组件的 `layer`/`order` 决定。
- **瓦片刷子**:图集按 `atlas_cols`/`atlas_tile` 切格点选,画到范围外自动扩格;
  拖动连续画聚合成**一条** `tilemap.paint` —— 于是整笔拖拽只占**一条撤销记录**
  (逐格入栈会让"撤销"要点几十次)。
- **撤销**:仍然是"场景 JSON 快照栈",但**快照里加了各瓦片地图的 CSV 文本**。
  原因:瓦片数据不在场景 JSON 里(`cols`/`rows`/`texture` 都是 `persist=0`,
  格子存在外部 CSV),只快照场景会导致"撤销了但瓦片还在"。
- **复制/粘贴/再做一个**:把实体的**全部运行时字段**抄成 JSON 再建新实体
  (走字段自省,而不是从场景 JSON 里抠一段再重编号 —— 场景 JSON 里的 `parent`
  是场景内索引,抠出来重编号很容易错)。
- **批量字段写** `comp.set_many`:拖动一组实体只产生一条撤销记录。
- **快捷键**:`1`/`2` 切工具、`F` 适应、`Ctrl+Z/Y`、`Ctrl+D` 复制、`Ctrl+C/V`、
  `Ctrl+A`、`Delete`、方向键微调(Shift 走一格网格)、滚轮缩放(以光标为锚点)、
  中键/空格/右键平移。

**新增命令**(全部在 `ds_model.c` 的 `ds_command` 里,前端与测试走同一条通道):

| 命令 | 作用 |
|---|---|
| `view.set {on?,x?,y?,zoom?}` | 设/关编辑器视图覆盖;无参数 = 回到场景相机 |
| `scene.render {x?,y?,zoom?}` | 离屏渲染一帧落 BMP,返回 `{url,seq,path,w,h,view}`(前端用 `?t=seq` 破缓存) |
| `scene.outline` | 每个实体的世界包围盒 + `kind`/`layer`(视口画框与图层面板的数据源) |
| `entity.duplicate {id\|ids,dx,dy}` | 再做一个(字段级复制 + 偏移) |
| `entity.copy {id\|ids}` / `entity.paste {dx,dy}` | 剪贴板(模型持有,跨场景有效) |
| `comp.set_many {items:[{id,comp,field,value}]}` | 批量写字段,**一条**撤销记录 |
| `tilemap.create {id,path,cols,rows,tex_path?}` | 先把 CSV 写出来再设 `path`(否则引擎的"设了就加载"必然报错) |
| `tilemap.info {id}` | 网格内容 + 几何(`tw/th/atlas_tile/atlas_cols/visible`)+ `atlas_url`(项目内图集的虚拟主机 URL) |
| `tilemap.set {id,col,row,tile}` | 画一格(越界自动扩) |
| `tilemap.paint {id,cells:[…]}` | 一次画多格,**一条**撤销记录 |
| `tilemap.csv {id,csv}` | 整图替换/清空 |

**自动化判据(不看屏幕)**

```bash
python main.py build-dexstudio          # 构建(模型 DLL + 两个宿主)
python tests/test_dexstudio.py          # 152 项:模型 132 + CLI 6 + WebView2 链 5 + …
dexstudio/host/dexstudio.exe --wv-selftest
#   PASS  前端已就绪(窗口 + 本地页面 + JS→C→JS 往返)
#   PASS  界面自测:21 项通过,0 项失败
```

`--wv-selftest` 不只等 `ui.ready`:它随后 `ExecuteScript("window.__ds_selftest()")`,
让**页面自己**验它那一层(渲染图是否真解码成 1024×640、画布上是否真有非背景像素与足够多颜色、
世界↔屏幕往返是否自洽、层级树行数、属性面板字段数、视口是否画出选中框、拖动是否写回位置、
瓦片是否落进 CSV 且能一次撤销),结果用 `ui.selftest` 消息回传,宿主断言"0 项失败"并作为退出码。

**已知简化(B3 一期)**

- 视口离屏尺寸固定 1024×640(引擎的离屏目标不可 resize),前端按比例缩放显示并画 letterbox;
  窗口更小或更大都不影响正确性,只是缩放显示。
- 帧内没有 PIE(§9.1 决策 #7):编辑期看到的是**静态一帧**,物理不跑。
- 图层只有分组与多选,没有真正的"拖拽排序/锁定"(顺序由组件字段决定)。
- 撤销快照里的 CSV 是**按路径**记的:如果某瓦片地图在快照那一刻还没有 CSV 文件
  (绕过 `tilemap.create` 手写 `path`),那一步之后画的第一笔撤销不回文件内容。
  正常流程(用 `tilemap.create` 建)不受影响。
- 复制/粘贴不带层级 `parent` 关系(新实体一律是根)。


### 9.4 B4 落地实况(逻辑编辑器)

**做出来的样子**

- **节点图**(`dexstudio/web/graph.js`):UE 蓝图式画布 —— 平移/缩放/网格、节点按分类
  配色、引脚、贝塞尔连线、拖节点、拖引脚连线、右键删节点/断输入、Delete 删选中。
  顶栏「场景 / 逻辑」切换(F1/F2),两个编辑器共用同一个窗口与同一条命令通道。
- **图 = 一棵 JSON DOM**,存 `<项目>/scripts/logic.json`。前端只画:节点长什么样、
  有哪些引脚与属性**全部来自 `graph.types` 自省** —— 与属性面板靠 `comp.schema`
  是同一套路,加节点类型不用改前端。
- **改图也能撤销**:撤销快照从"场景 JSON + 瓦片 CSV"推广成"场景 JSON + **不在场景里的
  文本文件**(路径 → 内容)",逻辑图与瓦片 CSV 共用这套机制。快照取的是**内存里的图**,
  不是磁盘上的旧文件(否则"改了没存"再撤销会退过头)。

**节点词汇表:为什么不照搬 bluedit**

`bluedit/` 是 **GAL(视觉小说)** 的编辑器,它的 42 种节点是背景/立绘/打字机/选项/
BGM 那一套 —— 对 2D 游戏逻辑没有用。所以 B4 **复用它的架构、换掉它的词汇**:

| 复用(架构) | 换掉(词汇) |
|---|---|
| 引脚用 `kind` 区分执行流 / 数据流,连线时必须同种 | 节点集合换成事件/流程/动作/条件,共 **22** 种 |
| 输出引脚可以扇出、生成器按执行链递归展开 | 动作直接读写**实体组件字段**(引擎的正解) |
| 界面靠模型自省画节点(不硬编码节点表) | 去掉 GAL 专有的变量/镜头/菜单概念 |

**与 bluedit 的三处刻意差异**(都在测试里钉住)

1. **一个输入引脚只能来一条线**。bluedit 允许多条汇入、`find_exec_target` 取
   `links` 里的**第一条** —— 于是"连线的先后顺序"变成了语义的一部分。这里直接拒绝
   第二条并说明原因:图的语义不依赖任何顺序。
2. **成环直接拒**(执行流与数据流都查)。bluedit 只在生成时按当前路径截断(输出一行
   `// 循环回边已截断`),而且它的 if 汇合点用全新 visited 展开,手工构造的图能无限
   递归。这里连线时就拒,生成时另有 4096 步兜底。
3. **失败必须带得出原因**。bluedit 的图操作几乎全是静默 `return`(全项目只有 3 条
   错误串,都在导出侧)。这里的 `graph.*` 一律返回 `{"ok":false,"error":"…"}`:
   引脚不存在 / exec 连了 data / 输入口已占用 / 属性名不认识 / 节点类型不认识 ……

**生成器**(`ds_graph_generate`)

```dex
include "dexgame";

func logic_start(dt: float) { ... }
func logic_update(dt: float) { ... }
func logic_draw(dt: float) { ... }
```

- **三个回调都收 `dt: float`**。DexLang **没有全局变量**,回调之间不能共享局部状态,
  所以 dt 只能当参数传;统一签名带来一个好处:`dt` 节点放在哪个事件里都合法
  (否则用户在"开始时"接一个 dt 就会生成编译不过的代码)。
- `on_action` / `on_key` 生成成 `logic_update` 里的
  `if (eng_action_pressed("jump")) != 0 { ... }` —— DexLang 没有事件回调,引擎给的
  就是轮询 API。
- **确定性**:事件节点按 `(y, x, id)` 排序后展开,生成器没有任何跨调用的计数器,
  同一份图永远生成同一份代码(测试断言"两次生成逐字节一致")。bluedit 的
  `_choice_seq` 是模块级全局、跨导出累积,同一进程里第二次导出就不是首次的结果了。
- 值引脚**没接线时回退到属性里的字面值**(`set_field.value` / `add_field.delta` /
  `branch.cond`):单放一个"写字段"节点就能用,想接表达式再接。
- 生成的语句一律带分号、缩进统一;条件写成 `if (<表达式>) != 0 {`,因为语言里
  没有三元运算符(实测 lexer 直接报 `?`)而布尔表达式可以当数值用
  (探针见 `_zigtmp/probe_syntax.dex` 里的三种写法,dexc 全部接受)。

**22 种节点**

| 分类 | 节点 |
|---|---|
| 事件 | `on_start` `on_update` `on_draw` `on_action`(动作刚按下)`on_key`(按键刚按下) |
| 流程 | `branch`(cond 可接线,也可用属性常数) |
| 动作 | `set_field` `add_field` `destroy` `play_sound` `camera_to` |
| 取值/条件 | `num` `dt` `field` `math` `compare` `action_down` `action_pressed` `key_down` `mouse_down` `on_ground` `mouse_world` |

**命令一览**(与前端走同一条通道)

`graph.types` / `graph.new` / `graph.info` / `graph.save` / `graph.generate` /
`graph.node.add` / `graph.node.remove` / `graph.node.set` / `graph.node.move` /
`graph.link` / `graph.unlink`

**项目模板**:`project.new` 现在同时写出空的 `scripts/logic.json` 与 `scripts/logic.dex`,
模板 `scripts/main.dex` 里 `include "logic"` 并调用三个回调 —— 新建的项目天生
"图驱动"而且**立刻能编译**(少了这一步,fresh 项目会因为 include 不到 `logic` 而编译失败)。

**自动化判据(不看屏幕)**

```bash
python tests/test_dexstudio.py      # 201 项(含逻辑图模型 24 + 代码生成 13 + 行为 6)
dexstudio/host/dexstudio.exe --wv-selftest
#   PASS  界面自测:34 项通过,0 项失败(无项目时为 32 项,生成那一组按 skip 记)
```

其中**行为那一组是 B4 的验收线**:建项目 → 造图(每帧 `x += 5`;按下 jump 时
`vy -= 400`)→ 生成 → 写 `main.dex` → `dexc.exe` 编译 → `vm.exe` 跑 4 帧 →
断言 `x=20`、`y=7`、`vy=0`。也就是说"图 → 代码 → 编译 → 真的按图跑"整条链是测过的,
不是只看"能不能编译"。

页面自测那一层还会验:切模式后画布**真的有了尺寸**(画布是在 `display:none` 状态下
建出来的,不 resize 就是 1×1 —— 这个坑当场被像素断言抓住)、节点面板按钮数 = 目录条数、
加节点后画布像素里有节点轮廓、选中框颜色出现、连线颜色出现、生成落盘。而且它
**不破坏用户已有的图**:只动自己加的三个节点,结尾删掉(连跑两次结果一致)。

**已知简化(B4 一期)**

- **没有用户变量**:跨帧状态直接读写实体组件字段(引擎的正解)。
  bluedit 的 `gal_var_*` 那套变量系统与 GAL 绑定,不搬。
- 节点里**没有随机数/文本拼接/计时器**;`destroy` 不做"延迟销毁"。
- `branch` 之后两条路各自结束(不生成汇合点),所以一张图里想"分支后再合流"就再放一个
  事件节点或用两个分支。bluedit 的菱形汇合优化没有搬(它的实现有无限递归的隐患)。
- 生成器只用 DexLang 确定有的语法(func/if/else/let/表达式/字符串);代码里没有
  注释以外的花活,便于以后 dexc 与 pyvm 双向对照。

## 11. 明确的非目标(一期)

- **不做** 3D(但渲染层不写死 2D 假设,便于以后扩展)
- **不做** 后处理与 2D 光照(二期以离屏 pass 链接入)
- **不做** 完整刚体动力学(旋转/关节/任意凸多边形)——需要时 vendor Box2D,不自己写
- **不做** DexLang 自定义组件(一期全 C 内置)
- **不做** 多线程(一期单线程,但预留边界)
- **不做** 二进制场景格式(M2 只做 JSON;导出期再加,复用同一张描述符表)
- **不做** IDE 的视口内即时试玩(PIE)与断点调试(决策见 §9.1 #7);编辑器基础功能
  (撤销/重做、复制粘贴、框选、网格吸附)则**要做**(§9.1 #8)
- **不做** 多光标、正则查找替换、多语言界面(一期只做中文界面)

## 12. 已知风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 改 ABI 触碰两个 VM,易不同步 | IDE 调试结果与真实运行不一致(历史上有过先例) | 双 VM 一致性断言(现有 `test_call`/`test_struct`/`test_memmodel` 已有此模式) |
| `vm.c` 重建后的二进制入库 | 二进制 diff 噪声大、不可审阅 | 先验证 `build-vm` 可复现(已列为开工前第一件事) |
| DirectWrite 起手陡峭(COM 接口) | M1 工期 | 先做最小可用路径:系统字体 + 字形图集 + 基础度量 |
| 描述符驱动一开始写起来更啰嗦 | M2 工期 | 它是 §7 结论的前提;若走手写路线则二进制格式不值得做 |
| 「按可扩展设计」目标模糊 | 可能过度设计或设计不足 | 一期坚持 AoS + 访问器封装,不直接暴露内存布局;等真实规模出现再决定是否 SoA |
| 物理的"简化"被当成 bug 反复排查(M3) | 圆角手感、堆叠抖动这类问题会消耗时间 | §6.5 把简化逐条列出来并写明**何时该修**;测试只断言引擎承诺的行为(精确落点、确定性),不断言近似路径的细节 |
